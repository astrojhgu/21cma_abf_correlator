# baseline_test_async.md —— 异步收包（`corr-async`）16384/1s 记录，以及一次换机器后的对照

写给**同步 / writer 独立线程那条线的会话**：这是异步接收版本在
`nch=16384 / 1 s 积分 / 24 路真实数据` 下的过程、原始数字、复现命令与干扰项，用来交叉比对。
与 `docs/baseline_test_sync.md` 配对；你们那份 §2.2 的方法学结论（"必须轮内轮转"）在本次
**被再次验证了一次，而且我是先犯错、后被数据纠正的**，见 §4.3。

- 时间：2026-09-20（本地时间），三台机器：`g01`（有别的用户负载）→ `g04`（安静但有硬阻塞）→ `g05`（安静且健康）
- 被测代码：分支 `high-timeres`，tip `340ef3c`（已 ff 合并进 master 并推送 `origin/master`）
- 参照代码：`master` 原 tip `aa5b3b2`（另一份 worktree 编译的二进制）
- 配置：`config/correlator-24-nf16384-manual.yaml`（g01/g04）与
  `config/correlator-24-nf16384-g05.yaml`（g05 专用，见 §3）
- 结论一句话：**同一台安静的机器上，异步版在生产几何下逐行补零 0.0000%、每站 0 丢帧、
  `sockdrop` 0，可以连续跑任意长；而"页锁定行缓冲有害"这类曾经从单窗口对比得出的结论是错的。**

## 3. 设备与环境：三台机器的对照（本次最大的教训是"环境比版本更能决定数字"）

| 检查项 | g01 | g04 | **g05（最终使用）** |
|---|---|---|---|
| 负载 | load 8–29（另一个用户的 6 核在跑） | load 0.3–1.0 | **load 0.26（空机）** |
| `net.core.rmem_max` | 2147483647 | **212992** | 2147483647 |
| 每站实得 `SO_RCVBUF` | 512 MiB | **0 MiB** | 512 MiB |
| 4× L20 不可纠正 ECC | 全 0 | **GPU1 = 1（坏）** | 全 0 |
| 数据网卡 | `ens2f0np0` = 172.23.0.11 | `ens2f0np0` = 172.23.0.41 | **`ens2f0np0` = 172.23.0.51** |
| 网卡所在 NUMA | node0（8 节点机，node0 只 4 核） | node0（2 节点 × 16 核） | node0（2 节点 × 16 核） |
| mlx5 中断向量 | 28 | 165 | 165 |

配置里两处**机器相关**字段因此必须按机器改（`tools/run-24-nf16384.sh` 现在会核对第二项）：

1. `receiver.interface_ip`：它同时是 `IP_ADD_MEMBERSHIP` 的 `imr_address`。写错的后果不是"少收几路"
   而是**一路都收不到** —— g05 刚接手时该网卡没有 IPv4 地址，`rx_packets/s = 0`。
2. `cpu.avoid_nic_interfaces`：那条规则的语义是"剔除网卡所在 NUMA 节点"。g01 的 node0 只有 4 核
   所以成立；g04/g05 是 2×16 核、网卡也在 node0，剔掉整节点只剩 16 核 < 需要的 28 核
   （24 收包 + 2 writer + pipeline + monitor），**`auto_layout` 直接拒绝编译**。g05 改为
   `avoid_nic_interfaces: []`，交给 auto_layout 按"NIC 中断最少的核优先"排序。

## 4. 结果

### 4.1 g05 生产几何基线（安静机器，4 张健康卡）

| 运行 | 行数 | lost | sockdrop | 补零均值 | 补零最大 | CPU 核 | fetch | release-wait |
|---|---|---|---|---|---|---|---|---|
| 首跑 150 s | 148 / 149 s | 88,637 | 0 | 0.0163% | 2.19% | 15.4 | 2.5 s | 3.1 s |
| 脚本验证 90 s | 88 / 89 s | **0** | **0** | **0.0000%** | 0.00% | 14.2 | 1.2 s | 1.4 s |
| 脚本验证 40 s | 39 / 39 s | **0** | **0** | **0.0000%** | 0.00% | 14.4 | 0.5 s | 0.5 s |

- 行率 **1.00 行/s**（1.0066 s 行长）；`2184960 帧 = 88 × 24576` 等逐次核对为**精确**。
- 24 站逐站 `gaps=0 lost=0 zero_filled=0`；`receive threads: 0 stalls >= 20 ms`。
- H2D 每卡 19.1 GB/s = **100% 链路**（这一档本来就在 98–103%）。

### 4.2 页锁定行缓冲 A/B：**无差别**（同一个二进制，只切一个环境变量）

两轮交替（pin0 → pin1 → pin0 → pin1），各 120 s，生产几何：

| 腿 | 行数 | lost | sockdrop | 补零 | CPU 核 | fetch |
|---|---|---|---|---|---|---|
| r1 pin0（可分页） | 119 | 0 | 0 | 0.0000% | 13.8 | 1.5 s |
| r1 pin1（页锁定） | 118 | 0 | 0 | 0.0000% | 13.9 | 1.5 s |
| r2 pin0 | 118 | 0 | 0 | 0.0000% | 13.9 | 1.6 s |
| r2 pin1 | 118 | 0 | 0 | 0.0000% | 15.4 | 2.4 s |

**结论**：在安静机器上，39 MB 行缓冲是否页锁定**测不出差别**。此前在 g01 上得到的
"页锁定使丢帧放大 159 倍"（`eea51d2` 的提交信息）**是错的**，成因见 §4.3。代码保留了
"行长 ≤4 MiB 才页锁定"这条闸门，但定性从"修回归"改为**保守选择**：生产几何继续走一直用的
可分页路径，页锁定只留在实测有收益的地方（4 站 1.31 MB 行上 1.35×）。`ac169d2` 已改正记录。

### 4.3 "必须轮内轮转"这条在本次被再次验证

g01 上同一个二进制、同一份配置、同一台机器：

| 时间 | 二进制 | 补零均值 | lost |
|---|---|---|---|
| 14:11 | 页锁定 ON | 0.7422% | 4,960,459 |
| 14:15 | master（参照） | **0.0049%** | 31,155 |
| 14:19 | 页锁定 OFF（硬编码） | 0.0052% | 12,011 |
| 14:23 | 页锁定 OFF（闸门） | 0.5753% | 2,993,883 |
| 14:25 | 同上 | **0.0000%** | 0 |
| 14:44 | 同上 | 0.3320% | 1,630,675 |
| 14:46 | master | **0.7920%** | 4,114,357 |
| 14:48 | 同上（41 s） | 0.0144% | 27,744 |

同一二进制在 12 分钟内可以从 0.0000% 跳到 0.7920%；而**交替**的一对腿里 master 反而比本分支差。
所以：**在 g01 上任何相隔数分钟的单次对比都无效**（与你们 §2.2 的结论一致：那台机器每 3–7 分钟
在两个状态间跳）。我早期正是用"隔几分钟的两次 150 s"得出结论，错了；正确做法就是你们写的
"把要比的臂放进同一窗口、顺序轮转"。**本文件只把 g05 的绝对值和交替腿的配对差当作结论。**

### 4.4 g04 的两个硬阻塞（记录，避免下次再花时间）

| 项 | 现象 | 判据/处理 |
|---|---|---|
| `net.core.rmem_max = 212992` | 每站 `SO_RCVBUF=0 MiB`（≈0.26 ms 缓冲）| **空载机器**上 4 站 1 s 行：每站 lost 3.3% / 4.1% / 6.9% / 0.02%，补零 5.8%；CPU 只用 1.6/32 核、load 1.0 → 与算力无关。需 root 抬 `rmem_max` |
| GPU1 不可纠正 ECC | `corr_create` 失败：`cudaSetDevice(1): cudaErrorECCUncorrectable` | **24 路 16384 必须 4 张卡**（每卡 H2D 恰好 19.2 GB/s = 100%），3 张是 25.6 GB/s 必然掉队 → 需 `nvidia-smi --gpu-reset -i 1` |

### 4.5 g05 特有的启动行为（会看到一次"拒绝启动"）

该机网卡只给 **15 个组**配了静态 `/32` 地址，配置用到的另外 **9 个组**
（239.1.148/149/150/151/162/170/171/172/173.3）是运行时才 join 的：它们的数据要等一个 IGMP 周期
才进内核，于是**第一次启动会被安全校验拦下**：
`station N: this station's first packet is … frames past the frame the run started at …`（退出码非 0，
未写任何文件）。**重试即成功**（实测如此）；要一劳永逸需 root 加那 9 个 `/32`。

### 4.6 短路长几何：行长与行率的交叉点（4 站 / 单卡 / `time_slice` / `rows_per_fetch=1`）

| frames_per_slot | 行长 | 实测行率 | 占数据率 | 库内占比 |
|---|---|---|---|---|
| 1 | 40.96 µs | 6333 /s | 25.9% | 87% |
| 4 | 163.84 µs | 5669 /s | 92.9% | 90% |
| 8 | 327.68 µs | 3052 /s | **100.0%** | 69% |
| 16 | 655.36 µs | 1526 /s | 100.0% | 43% |
| 32 | 1.31 ms | 763 /s | 100.0% | 32% |

- **行长 ≥327.68 µs 即跑满数据率**；1 帧那一档由 PCIe 决定：单卡每行要搬
  H2D 524 KiB + D2H 1.31 MiB = 1.83 MiB，19.2 GB/s 对应 10500 行/s，实测 8417–8952（**PCIe 上限的 85–93%**）。
- 每行字节数是硬约束：2/3/4 站（行长固定 40.96 µs）实测 15464 / 11513 / 8985 行/s，
  对应链路占用 10.1 / 13.6 / 16.5 GB/s。
- 取数实测速率：**页锁定目标 19.5–21.8 GB/s，普通可分页目标 12 GB/s**。
- 这一节的数据取自 g01，但都是在**同一窗口内连续扫描**得到的，且在工作站（4 站）上重复过两轮，
  量级可信；绝对值请以 g05 重测为准。

### 4.7 相位-频率与时间顺序的正确性验证（用重放器制造已知答案）

`corr-replay --pattern prng` 让所有站来自**同一条 splitmix64 采样流**、只差已知整数采样位移，
因此期望相位是精确的 `φ_k = -2πk·ΔN/M`（M = 2·n_freq），没有任何拟合自由度。

| 检验 | 注入 | 结果 |
|---|---|---|
| 静态时延（570 条基线） | stride 1/7/64、非均匀、负值、全零 | 最大时延误差 **0.0909 ps**；闭合残差 **0.0124 ps**；零延迟组残余 **5.079e-11 rad**；自相关 `\|Im\|/\|Re\| ≤ 1.83e-9` |
| 残余相位的量级 | — | 与"两站看的是同一随机流的不同窗口"理论 `√(\|ΔN\|/M)/√N帧` 一致（实测/理论 ≤ **1.038**） |
| 时间顺序阶梯（24 站 × 10 步） | 站 i 在第 k 步延迟 s·i·k 采样，每 1024 帧进一格 | 3000 个 (基线,步) 组最大误差 **410 fs**；阶梯起点与相关机首行帧号**完全对齐** |
| 负对照（故意错配） | 行号与步号错开一步 / 反转 / 相邻互换 | 误差 281 ns / 2.53 µs / 281 ns —— 比噪声底高 6 个数量级，**这个测试有牙齿** |
| 真实前端 | W17–N04（同板） | 时延 **719.3 ns**（全带拟合）/ **719.79 ± 0.215 ns**（逐行拟合，29 行）；其余 5 对跨板无相干（SNR≈1） |

### 4.8 前端换纪元：从"静默空转/叫停"到自动重置（2026-09-21）

前端换纪元在这台机器上是**常规事件**，一个晚上发生过两次（19:58 前后、01:16 那次是
停止发送而非换纪元，见 §4.9）。旧行为是：换纪元 → 每个包落在"起点之前"或"已完结帧之后"
→ 不产行、不报丢包 → 一直空转（早期），或停下等人（`StreamNotAdvancing` / `StreamQuiet`）。

现在相关机自己恢复，判据在**包号本身**（`assemble.rs::EpochLimits`，`StationAssembler::
epoch_check`）：

| 情形 | 判据 | 动作 |
|---|---|---|
| 计数器退回 | 某站的包比"已见最高帧"**落后**超过 `max(2 s 帧数, 1 行)` | 结束本次运行 → 重置观测 → 重新嗅探 → **另起一套**继续跑 |
| 计数器跳跃 | 某包比"已见最高帧"**超前**超过 `60 s 帧数` | 同上 |

为什么是这两个数：socket 缓冲能装 0.64 s 的包，所以"落后不到 2 s"是合法乱序/迟到；实测前端
最大空洞 3 s，而 60 s 留给它 20 倍余量。可用 `CORR_EPOCH_JUMP_S` / `CORR_EPOCH_BACK_S`
覆盖。重置由 `corr-async` 自己完成（`--max-epoch-restarts`，默认 10 次；0 = 停下等人），
日志里是：

```
corr-async: station 0: the packet numbering went backwards: ... instead of declaring 181908 frames missing
corr-async: resetting the observation and starting a new set (reset 1 of 10)
```

实测（corr-replay 造出的双向跳变，§4.9 同一套夹具）：第一段写 30 行后检测到退回，重置后
第二段在新起点继续写 42 行，两段各自成套、旧纪元的行完好；真实前端 60 s 运行触发 0 次重置。

注意一个固有的性质：**计数器退回**意味着新纪元的帧号比旧的小，所以两套的帧号区间可能重叠
——它们在不同的套里，`row_index` 也各自从自己的帧号算出，读数据要按套读。

### 4.9 顶到网卡时怎么判"是不是故障"

g05 生产几何下 `time_squeeze ≈ 70 /s`（只出现在 cpu0-15，即网卡 IRQ 所在节点），而同时：

- `softnet_stat` 的 **dropped 列 +0**；网卡 `rx_prio0_discards / buf_discard / cong_discard /
  out_of_buffer / buff_alloc_err / discards_phy` **全部 +0**；相关机补零 0.0000%、lost 0、sockdrop 0。

成因：4.69 Mpps 摊在 16 个管中断的核上 ≈0.29 Mpps/核，而一轮 NAPI 预算默认 300 包，约 1 ms 用完
→ 打满约 70 次/s。**预算打满只意味着软中断让出、下一轮接着收。**`tools/corr-web.py` 的收包卡原先
按 squeeze 判 warn（文案写"健康时应为 0"），在本机会常年报黄；已改为**按 dropped 判定**、
squeeze 作为压力值并列显示（提交 `340ef3c`）。

### 4.10 2026-09-20/21 夜间的停止：前端静默 vs 帧号不一致

20:53:36 起跑、正常跑 4.6 小时、16,404 行（午夜正确翻到新的一天那一套），01:16 停下。
报告给出的判据：24 站 `late=0`、`pipeline: 0 ring block episode(s)`、收包线程
15,482.8 s/站（93%）在等包、最长 43.99 s 无包 —— 是**前端停止发送**；而前端计数器单调
（01:16 时 3,858,726,912 个包，次日 5,034,839,929），**没有换纪元**。当时的看门狗把
"没有包"误报成了"帧号不一致"，原因是判据用了 `last_packet_ns`，而它在"停在环上"时会被
故意刷新。现在两种情形由**真实包计数**（`StationProgress::add_packets`）分开：
`StreamNotAdvancing`（包在来、放不下）与 `StreamQuiet`（所有站 60 s 一个包都没有，
`CORR_STREAM_QUIET_S`）。同一晚累计补零只有 0.0030%（173,391 帧 / 4.6 小时）。

## 5. 结论与置信度

**可以下的结论（强）**

1. **异步版在安静机器（g05）上、生产几何下是干净的**：多次 40–150 s 运行，逐行补零
   0.0000%、24 站 0 丢帧、sockdrop 0、行长精确（88 行 = 88 × 24576 帧），H2D 每卡 100%。
2. **短文（行长 ≥327.68 µs）不构成瓶颈**：行率 = 数据率；1 帧那一档由 PCIe 带宽决定（85–93%）。
3. **重放器定标的相位/时延验证全通过**：570 条基线最大 0.0909 ps、闭合 0.0124 ps，且残余相位
   与有限窗口理论一致 —— 共轭方向、bin 顺序、变换长度、跨包帧对齐、多卡 partial row 求和都正确。
4. **叶子级开关的取舍可以只靠交替 A/B 判定**：页锁定行缓冲在生产几何上无差别（4 腿全 0）。

**不能下的结论（弱/未知）**

- **任何来自 g01 的单窗口绝对值和单次对比都不可引用**（§4.3）：同一二进制 12 分钟内 0.0000% ↔ 0.7920%。
  我早期据此得出的"159 倍回归"已被推翻并改正（`ac169d2`）。
- 不能说"页锁定在所有几何下都无害"：只在 39 MB（生产）与 1.31 MB（4 站）两档测过，其余未测。
- 说不了"跨机器的绝对值可比"：g04 的 6% 补零完全来自 208 KiB 的 `rmem_max`，与代码无关。
- g01 那道"坏窗口"（每站等环 33–43 s/100 s、补零 20–25%）本次**仍未查清**，与你们 §6 的悬案是同一件事。

## 6. 干扰项（比对时必须一起报告）

1. **机器是否安静**：本次三台机器的结论差异几乎全部来自这里（§3、§4.3）。
2. **`rmem_max` / 实得 `SO_RCVBUF`**：必须随数字一起报；208 KiB 会让空载机器也丢 6%。
3. **GPU ECC**：坏卡会让 4 卡几何直接无法启动（g04）。
4. **网卡静态组播地址清单**：缺组会让首跑失败（§4.5）。
5. **`avoid_nic_interfaces` 与 NUMA 拓扑的匹配**：2×16 核机器上必须清空，否则拒绝编译。
6. 另一个用户的负载（g01 的 `21cma_eas_workbench`，10 进程 ≈6 核，与本机网卡/组播无关，纯 CPU）。

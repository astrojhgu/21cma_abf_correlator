# 设计：把 writer 移出管线线程

状态：**已实现并实测**（`writer.rs` 内部加一个写线程，`run.rs` / `pipeline.rs` / `report.rs`
一行不改）。§6 是实测结果，包括一条**对先前结论的更正**：`fsync_every_rows` 从 1 调到 10
并没有效果，之前"28% → 7.26%"是窗口漂移，**配置保持 1**。

## 1. 为什么要做

`writer` 一直在**管线线程**里同步跑：每关一行，它要写 300 个 baseline 文件（nch=16384 时一行
39 MB）并对每个文件 `fsync`（`storage.fsync_every_rows: 1`）。实测（2026-09-17 的 `/scratch`
NFS）：**一行 158 ms，其中 142 ms 是 300 次 fsync**（每次约 0.47 ms —— 贵的是**次数**不是字节：
同样 39 MB 写成 1 个文件，一次 fsync 只要 16.8 ms）。

而 nch=16384 的 GPU 管线**没有余量**：每卡 H2D 需求 4.80 GB/s，实测值就是 4.78–4.80 GB/s。
凡是让管线线程"停下来不喂 GPU"的事情，都会被放大成"环被关掉 → 收包线程写不进 staging →
socket 溢出 → 补零"。**写这一行的 158 ms 就是这样的停顿**，而且它发生在每一行。

注意 `fsync_every_rows: 10` **不能**解决它：那只是把 300 次 fsync 摊到 10 行里做
（每次仍然 0.47 ms/文件，摊薄后每行还是 ~14 ms，只是变成每 10 行一次 1.4 s 的突发）。
早期把 fsync 从 1 改到 10/100 看到"补零率 28% → 7–8%"，那是机器窗口漂移，不是 fsync：
§6.3 在同一窗口内对拍，1 与 10 的差别在噪声里（9.76/10.40、15.71/12.68、28.60/29.83、
8.00/9.24）。真正的修法是把写盘**整件事**搬出管线线程。

## 2. 做法

**一个写线程**，管线线程只做"把这一行的频谱拷进一个池化缓冲、投进有界队列"：

```
pipeline thread                       writer thread
  write_row(&[u8]) --copy--> buf --\
                                    >-- bounded queue (storage.queue_bytes) --> ensure_set_for
  write_row(...) -------------------/                                          write 300 files
  ...                                                                          fsync (+ sidecars)
  finish()  <-- ack(rows_written) ----------------------------------------------finish_set()
```

- **队列深度**由 `storage.queue_bytes` 决定（这个字段一直存在、一直被校验、从来没人用过，
  它就是为这件事准备的）：`depth = clamp(queue_bytes / row_bytes, 2, 8)`。nch=16384 时一行
  39.3 MB → 8 行 ≈ 314 MB；nch=4096 时 9.8 MB → 也是 8 行 ≈ 79 MB。写线程每行实测 128–140 ms
  （§6.1/§6.2），而行周期 1007 ms，所以队列**常态是空的**（实测最深 1 行）；它存在的意义是
  吸收抖动（一次 NFS 卡顿、一次 `fsync` 变慢 10 倍），而不是攒数据。
- **背压是有界的**：队列满了 `write_row` 会阻塞 —— 那就是改动前的行为，是诚实的回退；
  内存上限由 `queue_bytes` 兜住。
- **顺序与耐久性不变**：单消费者 FIFO，所以"先写频谱、后写 sidecar"的次序、以及
  `fsync_every_rows` 的语义都原样保留。切套（每日文件）现在发生在写线程里，因此
  切套那 ~0.5 s 的文件建立**不再占管线线程**。
- **错误延迟一行上报**：线程记下第一个错误后停止消费；管线线程在下一次 `write_row`
  或 `finish()` 时把它原样抛出 —— `RolloverFailed` 仍然是那个类型化错误，所以
  `pipeline.rs` 里"切套失败 → 新停止原因 + 报告"的路径不用改（最多晚一行，1 s 积分下 ≤1 s）。
  线程已经死掉时才发生的投递失败也会先去看它记下的错误，因为"线程停了"这句泛泛的话会
  把管线线程需要的类型弄丢（§6.4 有专门的测试）。
- **API 一行不改**：`Writer::open/open_with`、`write_row`、`finish`、`rows_written`、
  `dir`、`set_prefix/set_day/set_kind` 的签名全部保持，所以 `run.rs`（另一个会话正在改的文件）
  与 `pipeline.rs` 不需要任何改动。语义上唯一的变化是 `set_prefix/set_day/set_kind` 明确为
  "**本进程起始于**的那一套"（启动行要用它）：套名现在由写线程按首行时间戳决定，所以
  "这次运行到底产出了哪几套"要看目录里的文件，不看这个 getter。（新增 `Writer::sync()`
  给"不停止线程但要看到已交付的行"用，只有测试与监控需要。）
- **启动仍然同步**：发现当日已有的套、读 `ResumeState`、非每日布局下建文件，都还在
  调用者线程上（那时还没开 socket）。

## 3. 不做什么

- **不开 N 个写线程**：`fsync` 是串行开销，多线程只会让 sidecar 的"写完频谱再写它"次序
  跨线程，得不偿失；`storage.writers` 仍然是个未使用的字段（沿用现状，不假装它生效）。
- **不取消 fsync**：耐久性不拿来做性能交换。想把崩溃损失从"0 行"放宽到"N 行"用
  `fsync_every_rows: N`，那是另一个决定，与本次无关。
- **不改输出格式**（"300 个文件 300 次 fsync"的根因可以用"一天一个文件"消掉，但那是
  读端契约变更，先不动）。

## 4. 验收（结果见 §6）

1. `cargo test`（87 lib + 7 abi）/ `clippy`（0 条代码告警）全绿；本次没动 ABI 与 C 侧，
   `ctest` 不受影响；
2. **同样的 100 s / 300 s、同样的 nch=16384、`fsync_every_rows: 1`**、同一窗口与改动前对拍：
   补零率显著下降（§6.1/§6.2），每站等环从"从不低于 35 s"降到可以是 0；
3. 写线程和管线线程各报一行统计（线程：行数、每行自身耗时、每行墙钟耗时；管线线程：
   交付行数、队列最深积压、以及"管线线程一次都没写盘/fsync"），用来证明"交接"真的发生了；
4. 切套（`tools/daily_rollover_test.sh`）仍然全过 —— 现在它在写线程里发生，切套对管线线程的
   代价实测 **3 ms**（§6.4）。

## 5. 这条不解决什么

这台机器有"坏窗口"：同一份代码、同一份配置，补零率会在 0.0000% 与 ~25% 之间跳，周期约
3–7 分钟，与 fsync、与写线程都无关（§6.2 里 n1 与 n10 在同一轮里可以相差 ±25 个百分点）。
坏窗口里收包线程仍会等 staging 环 33–40 s/100 s，说明**环被关闭还有第二个原因**，它不在
writer 这边（GPU 侧吞吐？别的会话在抢机器？这台机器的坏窗口本身还没有解释清楚）。
写线程只保证一件事：**写盘不再占管线线程**，因此"写盘"这一项从此可以排除在嫌疑之外。

## 6. 实测（2026-09-17 21:00–22:30，24 路真实数据，nch=16384，1 s 积分）

### 6.1 背靠背 300 s，`fsync_every_rows: 1`（21:25 vs 21:30，load 都是 27.3）

| | 改动前（`4410e09`） | 改动后 |
|---|---|---|
| 补零率（逐行，`longrun_report.py`） | **29.0060%** | **0.0155%** |
| 完全干净的行 | 1 / 297 | 213 / 297 |
| 管线线程在库调用里 | 98.6 s（33%） | 25.7 s（9%） |
| ├ release-wait | 87.6 s | 13.3 s |
| └ 每站等 staging 槽 | 122.5 s | 0.1 s |
| 写线程自身耗时 | （在管线线程上） | 128 ms/行（行周期 1007 ms），队列最深 1/8 |

### 6.2 配对实验：100 s × 6 轮 × 3 臂，轮内轮转（拉丁方）

单次 300 s 的对比说明不了问题：这台机器的好坏窗口约 3–7 分钟一跳，而好坏之间差 20 多个
百分点。所以三臂**在同一窗口内**各跑 100 s，顺序每轮轮转；6 轮之后每个臂在每个位置上
各出现两次，位置偏差被抵消（实测第一位的运行确实偏好：位均 6.3% / 14.1% / 16.0%）。

| 轮次（顺序） | 改动前 fsync=1 | 改动后 fsync=1 | 改动后 fsync=10 |
|---|---|---|---|
| 1（前,后1,后10） | 28.0899% | 15.3172% | 0.0000% |
| 2（后1,后10,前） | 20.4843% | 2.2165% | 8.9726% |
| 3（后10,前,后1） | 10.0307% | 0.0106% | 0.1345% |
| 4（前,后1,后10） | 7.0582% | 0.1111% | 24.6741% |
| 5（后1,后10,前） | 28.9530% | 0.0000% | 22.2753% |
| 6（后10,前,后1） | 27.5689% | 21.9084% | 0.0135% |
| **均值 / 中位数** | **20.36% / 24.03%** | **6.59% / 1.16%** | **9.35% / 4.55%** |

改动前后（同为 fsync=1）**6/6 轮都更差**，逐轮差值 +12.8 / +18.3 / +10.0 / +6.9 / +29.0 /
+5.7（中位数 +11.4 个百分点）。收包线程等 staging 槽（每站，100 s）：改动前 39.7 / 40.8 /
34.8 / 43.4 / 41.0 / 39.7（**从不低于 34.8 s**），改动后 0.0 / 23.0 / 33.7 / 0.0 / 0.1 / 0.1
（好的窗口里是 0）。

### 6.3 fsync 这个旋钮：同窗口内对拍（旧二进制）

| 轮次 | fsync=1 | fsync=10 |
|---|---|---|
| 7 | 10.40% | 9.76% |
| 8 | 12.68% | 15.71% |
| 9（坏窗口） | 29.83% | 28.60% |
| 10 | 9.24% | 8.00% |

没有差别（连坏窗口里也一样）。所以：**配置保持 `fsync_every_rows: 1`**（崩溃最多丢 0 行），
早期"1 → 10 把补零率从 28% 降到 7.26%"是窗口漂移；把 fsync 摊薄本来也省不下多少
（0.47 ms × 300 次是**按次**计费，摊到 10 行只是变成突发）。新二进制里 fsync=1 与 fsync=10
同样分不出差别（6.2 表里符号不一致），这也正好说明写线程之后这个旋钮与补零率脱钩了。

### 6.4 切套与自检

- `tools/daily_rollover_test.sh`：2 个套、前缀各自等于该套首行的本地时间、row_index 与
  frame grid 跨边界连续、24 行对得上、**切换对管线线程的代价 3 ms**、新套 304 个文件在
  首行后 546 ms 内全部出现、整场补零 0 帧。
- 新增测试 `a_rollover_that_cannot_open_its_set_stops_with_that_reason`：切套失败这一路径
  现在发生在写线程里，测试证明错误跨线程后**仍然是 `RolloverFailed` 类型**（管线线程要用它
  做 `StopReason`），而且运行是在"下一行/`finish()`"处报告，不是丢掉。
- `writers`（写线程数）仍然是未使用字段，本文不假装它生效。
